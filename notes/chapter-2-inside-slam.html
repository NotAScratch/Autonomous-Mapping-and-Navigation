CHAPTER 2Inside the machine

How each box in the SLAM loop actually does its job.

Where did ch. 1 leave off?
  • SLAM repeats predict (odometry) → correct (sensor).
  • Errors pile up as drift; loop closures pull it back.
  • Modern SLAM is graph-based: poses are nodes, measurements are edges.
  • Front-end builds the edges. Back-end optimises the graph.

What does odometry actually give us?

Wheel encoders count ticks → distance rolled by each wheel, dL and dR. For a differential-drive robot with wheel spacing b:

d = (dL + dR) / 2     Δθ = (dR − dL) / b

Integrate these every tick → odom pose. Smooth, fast, and always drifting.

How is one move described?

Split any move from pose A to pose B into turn → drive straight → turn:

δrot1 = atan2(y′−y, x′−x) − θ δtrans = √((x′−x)² + (y′−y)²) δrot2 = θ′ − θ − δrot1
Where does the noise go?

Each of the three parts gets its own noise. The noise grows with the size of the move:

σ²rot1 = α1δ²rot1 + α2δ²trans

(similar for trans and rot2). The α's are tuning knobs. Nav2's AMCL exposes them as alpha1 … alpha5.

Why a banana and not an ellipse?

A small heading error × a long distance = a big sideways error. So the cloud bends around the start point. An EKF squashes it into an ellipse; that mismatch is one source of linearisation error.

Calibrate first Measure b and the wheel radius carefully. A 2% error in b is a 2% error in every turn, so about 7° lost per full rotation.
Summary

Odometry gives a turn-drive-turn guess. Its uncertainty grows with distance and turning, and it bends into a banana shape.

What's the sensor model?

p(z | x, m) = "if I'm at x in map m, how likely is this scan?" Used to score a pose guess.

  • Beam model: traces every ray. Mix of 4 cases: hit the wall, something closer (a person), max range, random junk. Accurate but slow.
  • Likelihood field: precompute, for every map cell, the distance to the nearest wall. Score each scan endpoint by how close it lands to a wall. Fast and smooth, so it's what most 2D systems use.
What is ICP?

Iterative Closest Point lines up a new scan (orange) with a reference (teal):

  1. Pair each scan point with its nearest map point.
  2. Throw out pairs that are too far apart (likely outliers).
  3. Solve for the R, t that best overlaps the pairs (closed form, via SVD).
  4. Move the scan. Repeat until the change is tiny.

Variant: point-to-line ICP (PL-ICP) converges in fewer steps on walls.

When does it fail?
Watch out
  • Bad initial guess → locks onto the wrong wall (local minimum). That's why odometry feeds in first.
  • Long featureless corridor → scan can slide along it; the forward direction is unconstrained.
  • Moving people → pairs with things that aren't in the map.
What do real systems use?
  • slam_toolbox (Karto-based): correlative scan matching. Brute-force tries a grid of (x, y, θ) around the guess, scores each with the likelihood field, then refines. Hard to fool with a bad initial guess.
  • Cartographer: scan-to-submap matching solved with Ceres, plus branch-and-bound search for loop closures.
Summary

The sensor model scores a pose. Scan matching searches for the pose with the best score, and its result becomes an edge in the graph.

What's a "feature"?

A small patch that's easy to find again: a corner, not a blank wall.

  • Detector says where (e.g. FAST corners).
  • Descriptor says what it looks like (e.g. BRIEF = a 256-bit string).
  • ORB = Oriented FAST + Rotated BRIEF. Fast and rotation-invariant, used by ORB-SLAM.
How are features matched?

Compare descriptors by Hamming distance (count the differing bits). Then use RANSAC to find the camera motion that most matches agree on; the rest are thrown out as outliers.

How do we get 3D from 2D?

One image only gives a direction. You need two views (or a depth sensor) to fix where along the ray P sits.

Why can't mono know scale?

A scene twice as big and twice as far away gives the exact same image. Mono SLAM maps in unknown units. Fix it with a stereo baseline, a depth camera, an IMU, or a known-size object.

Keyframes and bundle adjustment?

Keyframes: don't keep every frame. Add one when the view has changed enough (e.g. too few features still tracked).

Bundle adjustment: nudge keyframe poses and 3D points together so every point re-projects onto where it was actually seen:

min Σ ‖ uij − π(Ti, Pj) ‖²

π = project 3D point into the camera. Error = reprojection error in pixels. Usually run on a local window of recent keyframes.

Summary

Find corners, match them, triangulate them, and refine with bundle adjustment. Mono can't see scale, so add depth or an IMU.

What are we minimising?
F(x) = Σ eij(x)T Ωij eij(x)

The total weighted disagreement over all edges. It's nonlinear because of the angles (sin, cos), so there's no one-shot answer. We linearise and iterate.

How does Gauss-Newton work?
  1. Linearise each edge: e(x + Δx) ≈ e + J Δx
  2. Build H = Σ JTΩJ and b = Σ JTΩe
  3. Solve H Δx = −b
  4. x ← x + Δx, then repeat. A handful of iterations is usually enough.
Why is it fast?

Each edge touches only 2 poses, so H is mostly zeros: a diagonal band from odometry plus a few off-diagonal blocks from loop closures. Sparse Cholesky solves thousands of poses in milliseconds. Libraries: g2o, Ceres, GTSAM.

Gauge freedom?

All edges are relative, so the whole graph could slide or spin and F wouldn't change. H is then singular. Fix x₀ (anchor the first pose) and it's solvable.

Gauss-Newton vs Levenberg-Marquardt?
(H + λI) Δx = −b

LM adds damping λ. Big λ gives small, careful steps (like gradient descent); small λ behaves like Gauss-Newton. λ adapts: if a step makes F worse, raise λ and try again.

Classic bugWrap angle errors into [−π, π]. Otherwise 359° vs 1° looks like a 358° error.
Summary

Linearise, solve the sparse system H Δx = −b, update, repeat. Anchor the first pose and wrap the angles.

How do we recognise a place?
  • Camera, bag of words: cluster descriptors into a "vocabulary" offline. Each image becomes a histogram of visual words. Compare histograms to find look-alike past frames (DBoW2, in ORB-SLAM).
  • 2D LiDAR: match the current scan against old submaps near the current estimate.
  • 3D LiDAR: global descriptors such as Scan Context.
Should we trust a match right away?

No. Before adding the edge, check:

  1. Geometry: RANSAC / scan-match score must be good.
  2. Consistency: several frames in a row agree.
What if a bad edge gets through anyway?

With plain squared error, one wrong edge with error 10 pulls 100× harder than an edge with error 1. One bad loop closure can wreck the whole map. Robust kernels cap that pull:

Stronger options: switchable constraints or DCS, which let the optimiser turn a bad edge's weight down to almost zero.

Summary

Recognise places with BoW or submap matching, check them geometrically and over time, and wrap the edges in robust kernels to protect against mistakes.

What do we compare against?

Ground truth: motion capture, RTK-GPS, or a benchmark dataset: TUM RGB-D (indoor RGB-D), KITTI (car, LiDAR + stereo), EuRoC (drone, stereo + IMU).

ATE vs RPE?
  • ATE (absolute trajectory error): align the two paths, then take the RMSE of the red lines. Tells you about global consistency.
  • RPE (relative pose error): error in the motion over a fixed step, e.g. per 1 m. Tells you about drift.
Tool to compute them?
# pip install evo evo_ape tum groundtruth.txt estimate.txt -va --plot evo_rpe tum groundtruth.txt estimate.txt --delta 1 --delta_unit m

-a aligns the paths first. Formats: tum, kitti, euroc, bag.

No ground truth on my robot?
  • Tape a start mark. Drive a loop and stop on the mark. How far off is the reported pose?
  • Measure a real corridor with a tape. Compare it with the length in the map.
  • Look for doubled or blurry walls. Sharp walls usually mean good scan matching.
