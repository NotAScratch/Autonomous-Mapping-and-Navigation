CHAPTER 0, BEFORE SLAMROS 2 basics

A ROS 2 robot isn't one big program. It's lots of small programs (nodes) that pass messages to each other over named channels (topics).

oval = nodebox = topicarrow = message flow

This is exactly how rqt_graph draws a running robot.

0.1
nodes & topics

Nodes

  • One process (or part of one) doing one job: read the LiDAR, run SLAM, drive the motors, show RViz.
  • Each has a name, e.g. /slam_toolbox.
  • Written in Python (rclpy) or C++ (rclcpp).
  • Why split things up? If one node crashes the others keep going, and you can swap one (a different LiDAR driver) without touching the rest.

Topics

A named stream of messages, like a radio channel. Nodes publish to it or subscribe to it.

  • Many-to-many: any number of publishers and subscribers on one topic.
  • Anonymous: the publisher doesn't know who's listening, and doesn't care.
  • One-way, continuous: no reply. Best for data that keeps flowing.

messages & QoS

Messages

Every topic carries exactly one message type: a fixed structure defined in a .msg file. Publisher and subscriber must agree on it.

Many messages start with a header: a timestamp (when) and a frame_id (which frame, e.g. laser). SLAM needs both, which links straight to the tf tree in ch. 1.

# geometry_msgs/Twist Vector3 linear # x = forward m/s Vector3 angular # z = turn rad/s # see any type: ros2 interface show \ geometry_msgs/msg/Twist

QoS (quality of service)

New in ROS 2, and the source of a lot of "connected, but nothing arrives" bugs. Each publisher and subscriber chooses:

  • Reliability: RELIABLE resends lost messages. BEST_EFFORT just drops them, which is fine for fast sensor data.
  • Durability: VOLATILE = late joiners only get new messages. TRANSIENT_LOCAL = the last message is kept for late joiners. /map uses this, so RViz opened later still gets the map.
  • History / depth: how many messages to queue.

does it connect?

publisher ↓ · subscriber →RELIABLEBEST_EFFORT
RELIABLE✓✓
BEST_EFFORT✗✓
The classic bug LiDAR publishes BEST_EFFORT, RViz subscribes RELIABLE, and you get no points and no error. Check with ros2 topic info /scan -v, then set RViz's reliability to Best Effort.

Same idea for durability: a TRANSIENT_LOCAL subscriber won't match a VOLATILE publisher.

4 ways to talk

Topics aren't the only way

Topic

Continuous stream, many listeners. e.g. /scan, /cmd_vel

Service

Ask once, get one answer. Quick calls. e.g. save the map, reset odom

Action

Long task with progress updates; can be cancelled. e.g. Nav2 navigate_to_pose

Parameter

Settings that live on a node. Set in YAML or at launch. e.g. map resolution

Rule of thumb Streaming data → topic. A quick question → service. "Go do this, keep me posted" → action. A config value → parameter.

names · discovery · launch

Names & namespaces

  • /scan starts with /, so it's absolute and always means exactly /scan.
  • scan has no slash, so it's relative and picks up the node's namespace: in namespace robot1 it becomes /robot1/scan.
  • That's how two robots share a network without their topics colliding.

remapping = rename without touching code

Your driver says /lidar/scan but SLAM wants /scan:

ros2 run my_driver lidar_node --ros-args -r /lidar/scan:=/scan

How do nodes find each other?

No central server. (ROS 1 needed roscore.) ROS 2 runs on DDS, and nodes discover each other automatically on the network.

ROS_DOMAIN_ID splits robots into separate groups. Nodes only see others with the same ID.

Laptop can't see the robot's topics? Same ROS_DOMAIN_ID on both? Same Wi-Fi? Firewall letting multicast through? (ROS_LOCALHOST_ONLY=1, or ROS_AUTOMATIC_DISCOVERY_RANGE on newer versions, keeps it to one machine.)

Launch files

Starting 10 nodes by hand is painful. A launch file (Python, XML or YAML) starts them all together, with their parameters, remaps and namespaces:

ros2 launch slam_toolbox online_async_launch.py

first node + cheat sheet

A tiny obstacle-avoider

One node: subscribes to /scan, publishes to /cmd_vel.

import rclpy from rclpy.node import Node from rclpy.qos import qos_profile_sensor_data from geometry_msgs.msg import Twist from sensor_msgs.msg import LaserScan class Avoider(Node): def __init__(self): super().__init__('avoider') # node name self.pub = self.create_publisher(Twist, '/cmd_vel', 10) self.create_subscription(LaserScan, '/scan', self.on_scan, qos_profile_sensor_data) # best-effort, matches LiDAR def on_scan(self, msg): # runs on every scan mid = len(msg.ranges) // 2 ahead = min(msg.ranges[mid - 10 : mid + 10]) cmd = Twist() cmd.linear.x = 0.15 if ahead > 0.5 else 0.0 cmd.angular.z = 0.0 if ahead > 0.5 else 0.6 self.pub.publish(cmd) rclpy.init() rclpy.spin(Avoider())

⚠ Which index is "straight ahead" depends on how the LiDAR is mounted. Check angle_min and angle_increment first.

when it doesn't work

Debug, top to bottom

  1. Is the node running?ros2 node list. If it's missing, check the terminal it crashed in.
  2. Is the topic there, with the exact name?ros2 topic list. Look for typos, a missing /, or a namespace prefix.
  3. Is data actually flowing?ros2 topic hz /scan. 0 Hz means look at the publisher.
  4. Does the QoS match?ros2 topic info /scan -v. Best-effort into reliable = silence.
  5. Can the machines see each other?Same ROS_DOMAIN_ID, same network, firewall open.
  6. Do time and frames line up?use_sim_time right? Clocks synced between machines? tf tree complete? (ros2 run tf2_tools view_frames)
Chapter 0 in one breath Nodes do one job each. They talk over topics (streams), services (ask/answer) and actions (long tasks), are configured with parameters, find each other automatically through DDS, and get started together by launch files.
