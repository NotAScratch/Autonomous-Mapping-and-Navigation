SLAMSimultaneous Localization And Mapping

A robot is dropped into a place it has never seen. It has to build a map of the place and, at the same time, figure out where it is on that map. Nobody gives it either one.

the chicken-and-egg problem

what's being estimated

p( x1:t , m  |  z1:t , u1:t )
  • x = robot pose (x, y, θ in 2D) at each time step
  • m = the map
  • z = sensor readings (laser scans, camera images)
  • u = controls / odometry (what the wheels or IMU say we did)

Read it as: "given everything I've seen and every move I've made, what's the most likely path and map?" It's a probability, because every sensor is noisy.

Key idea Estimate pose and map together, and always keep track of how unsure you are about each.
p. 2

The SLAM loop

Every SLAM system repeats the same cycle many times a second:

  1. Move: wheel encoders / IMU tell us roughly how far we went and how much we turned.
  2. Predict: apply the motion model. The new pose is a guess, and it's fuzzier than the last one.
  3. Sense: LiDAR scan or camera frame.
  4. Match: "this wall in my scan is that wall in my map." This is called data association, and it's where most bugs come from.
  5. Correct: shift the pose so the scan lines up, then add the new readings to the map. Uncertainty shrinks.

the maths behind it (Bayes filter)

bel(xt) = η · p(zt | xt) · ∫ p(xt | xt−1, ut) bel(xt−1) dxt−1
  • red part = motion model → predict
  • green part = sensor model → correct
  • η just normalises so it all sums to 1
p. 3

Drift & loop closure

Odometry is never perfect: wheels slip, the floor is uneven, the IMU has bias. Tiny errors add up with every step, so the estimated path slowly peels away from the real one. That's drift.

loop closure

When the robot comes back to a place it has already mapped and recognises it, that gives one strong constraint: "pose now ≈ pose back then." The optimiser spreads the correction back along the whole path, and the map snaps into shape.

  • LiDAR: match the current scan against old submaps
  • Camera: "bag of words" image matching (place recognition)
⚠ careful A false loop closure (two similar-looking corridors) bends the whole map wrong. Good systems double-check before accepting one.
p. 4

3 families of SLAM

(roughly oldest → newest)

① EKF-SLAM

filter · 1990s

One big state vector: robot pose + every landmark. Keeps a covariance matrix linking them all.

+ simple, classic
− cost grows as n² with landmarks
− linearisation errors

② Particle filter

FastSLAM · GMapping

Many "particles," each a guess of the robot's path with its own map. Bad guesses die off, good ones get copied.

+ handles non-Gaussian noise
− needs lots of particles in big spaces

③ Graph-based

today's standard

Store poses as nodes, measurements as edges. Then solve for the poses that best agree with every edge.

+ scales well, re-optimises after loop closure
+ used by Cartographer, slam_toolbox, ORB-SLAM

pose graph, drawn out

Each edge says "these two things should be this far apart," with some error e. Solve:

x* = argminx Σ eijT Ωij eij

= nonlinear least squares. Ω = information matrix, i.e. how much we trust that edge. Solvers: g2o, Ceres, GTSAM.

front-end

Turns raw sensor data into edges: scan matching, feature tracking, loop detection.

back-end

Takes the graph and optimises it into the best set of poses (the argmin above).

p. 5

Sensors & maps

what it sees with

  • 2D LiDAR: one slice of distances. Cheap, reliable indoors.
  • 3D LiDAR: full point clouds, works outdoors.
  • Mono camera: cheap, but can't tell scale by itself.
  • Stereo / RGB-D: camera + depth, so scale is known.
  • + IMU: fills the gaps during fast motion (VIO / LIO).

what map it builds

  • Occupancy grid: cells marked free / occupied / unknown. Standard for 2D navigation.
  • Landmark map: a list of feature points.
  • Point cloud: raw 3D points.
  • Voxels / OctoMap: 3D occupancy grid.

well-known systems

  • GMapping: particle filter, 2D LiDAR, needs odometry
  • Hector SLAM: 2D LiDAR, works without odometry
  • Cartographer (Google): graph-based, 2D/3D LiDAR, submaps
  • slam_toolbox: graph-based 2D LiDAR, the default SLAM for ROS 2 Nav2
  • ORB-SLAM3: visual, mono/stereo/RGB-D with optional IMU
  • RTAB-Map: RGB-D / stereo / LiDAR, strong loop closure
  • LIO-SAM: 3D LiDAR + IMU, outdoors

On a real ROS 2 robot

the frames (tf tree)

SLAM publishes map → odom, which is the drift correction. Odometry stays smooth but drifts; SLAM nudges it back into place.

slam_toolbox in 3 commands

# 1. start SLAM (robot's lidar + odom already running) ros2 launch slam_toolbox online_async_launch.py # 2. drive around slowly (teleop), watch the map in RViz ros2 run teleop_twist_keyboard teleop_twist_keyboard # 3. save the map when it looks right ros2 run nav2_map_server map_saver_cli -f my_map

tips for a clean map

  • Drive slowly, and turn slower still. Fast spins blur scans.
  • Come back to the start so a loop closure happens.
  • Check the laser's position in the URDF. A wrong offset gives doubled walls.
  • Good odometry makes for an easier SLAM. Calibrate wheel size and wheel spacing.
  • Long blank corridors and glass are hard: few features to match.
One-line summary SLAM = predict where you moved, check it against what you see, fix both the pose and the map, and use loop closures to undo drift.
